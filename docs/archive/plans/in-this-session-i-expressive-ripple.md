- **A follow-up deep-dive pass** on capabilities Daniel flagged as missing from the first scan (the worksheet's own questions don't know to ask about them): the iPad-as-companion-gesture-input-surface pairing with the desktop app, thumb-joystick lateral pan across tileable wallpaper forms, and the full depth of conduit's capability-detection/negotiation layer. All three are shipped and substantial (details below) — confirming the worksheet's fixed question list undercounts what's actually built.

Daniel's guidance on how to proceed (from the pre-plan Q&A, plus a correction after the first plan draft):
- Edit **inline**, directly in the worksheet — one document, not a companion doc.
- Do **not** frame divergent material as "contradictions to resolve." Most GTM thinking is loosely held. Present multiple threads as **complementary hypotheses still finding their shape**, not conflicts.
- Material that doesn't map to any worksheet question goes in a **new appendix section** at the end, not forced into existing questions and not dropped.
- **Part 1's purpose is broader than answering the worksheet's questions.** The questions are a starting point, not the ceiling — the app has rich shipped capabilities the questionnaire doesn't know to ask about. Part 1's real job is to function as a **full capability inventory**, and for each capability, to flag **plausible tier/SKU gating hypotheses** (illustrative, not decided) — e.g. 49MP capture + motion stabilization might gate to Studio/Motion tiers, keyframe animation + HDMI/AirPlay might gate to a Motion tier, MIDI + Syphon/NDI might gate to a Live Performance tier. This inventory is what eventually becomes a feature-comparison table for buyers, so completeness and clear tier-boundary thinking matter more than answering each worksheet question narrowly.
- **Gumroad-vs-App-Store distribution is an open strategic question, not a settled comparison.** App Store sandbox gating for Syphon has never actually been tested — treat "Syphon is blocked in the sandbox" as unconfirmed, not fact. NDI-to-a-local-Arena-instance already reads as a genuinely good experience today, which raises the real question: is Syphon meaningfully superior enough to justify its own distribution path, and how much does that depend on how heavily Fold ends up targeting live VJ artists as early adopters? Present this as the open question it is.

**Part 1 (What is actually built) — restructured as a full capability inventory, not a narrow Q&A pass.** Organize by functional area (forms & mirror math; source-region interaction, including multi-surface input; motion & procedural drift; live/Perform mode; resolution/export/color; conduit broadcast & platform detection; the control/input layer; instrumentation). Capabilities confirmed in the deep-dive pass that must appear here even though the worksheet never asks about them directly:
- **iPad-as-companion-gesture-input-surface** — a real-time pairing where an iPad/iPhone controls a desktop Electron session: hand-rolled WebSocket+HTTP server on the LAN, QR-code pairing with a per-session token, bidirectional state stream (phone sends touch-zone gestures, desktop streams back live slice-outline geometry + rendered overlay affordances so the phone's crosshairs track exactly), synthetic touch-event dispatch onto the desktop's real interaction handlers for full parity. Fully shipped, in daily use. (`electron/remote-input.js`, `src/shell/remote-input.js`, `src/shell/input-bus.js`)
- **Thumb-joystick lateral pan across tileable wallpaper forms** — a reusable velocity-joystick component with a latch/drift toggle, mounted twice per session (canvas pan + Droste Möbius-offset), wrapping seamlessly against each form's hand-derived lattice period; also mappable from physical gamepad thumbsticks via the Gamepad API. Fully shipped. (`src/components/pan-joystick.js`, `src/engine/forms/{square,hex,triangle}.js`, `src/shell/gamepad-input.js`)
- **Conduit's negotiated capability-detection/broadcast layer** — deeper than "which destinations exist": a host-capability contract every native shell must satisfy (with an all-false no-op web host so nothing can misfire), detection that's never speculative (a destination never appears in a picker unless the native addon/SDK actually loaded), an adaptive pixel-readback prober that times and checksum-validates multiple GPU→CPU paths per-device and picks the fastest *correct* one (catching e.g. an iPad WebKit R/B channel swap bug automatically), shared codec-negotiation for record/export, and per-destination broadcast mechanics (Syphon arm/disarm, NDI fixed-cadence pacing tuned against WiFi jitter, a distinct binary wire protocol for iOS NDI over localhost WebSocket, and a zero-readback "second engine instance" architecture for output-window/HDMI/AirPlay with an adaptive degradation ladder under memory pressure). (`packages/conduit/src/{host,capture,encode,syphon-sink,ndi-sink,frame-wire}.js`)
- **Perform mode's hold/take/cut transport** — a third editing mode where edits stage live while the broadcast output eases toward them via a perceptual-ramp follower, with an onion-skin ghost trail showing the chase path. Fully shipped. (`src/shell/perform-runtime.js`)
- **The Control Bus (Arc 6)** — one normalized signal pool unifying MIDI, gamepad, native trackpad gestures, and the companion-surface gestures behind a single LEARN-based mapping admin with savable "rig" presets. Fully shipped; a spec-v2 unification of its currently-fragmented control-metadata lists is in progress. (`src/shell/input-bus.js`)
- **Multi-clip source staging / clip queue** — explicitly planned, not built; call this out as a maturity distinction from Perform mode itself, which is shipped. (`docs/BACKLOG.md`)
- **Perf-ledger / thermal-pressure instrumentation** and the **shared-socket native video architecture** (iOS single-decode sharing between main view and external display) — real, active infrastructure worth a line each, conduit-adjacent rather than a broadcast destination per se.
